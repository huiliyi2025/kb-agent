# 0.2.0 深度优化与验证报告

日期：2026-10-22。本报告记录 kb-agent 在 0.1.0 基础上进行的可靠性、安全与工程化改进，以及对应的测试与评测证据。

## 1. 原项目评价

原项目已经有完整的业务主线：多格式解析、分块、两路检索、RRF、重排、资料充分性判断、引用、SSE、Agent、认证和离线评测。分层清楚，Protocol 使模型可以替换，FakeLLM 有利于脱离网络验证行为。

主要不足不在于功能名不够多，而在于部分关键约束尚未贯穿所有链路：认证用户身份没有进入检索；会话仅按 ID 复用；索引判重存在并发窗口；同步与流式结果处理不一致；此外缺少依赖声明、实际测试、样例数据与说明文档。本轮围绕这些可验证的问题升级。

## 3. 行为变化和兼容性

1. **权限更严格。** 问答、Agent、目录、片段和删除只访问当前用户资源。原来依赖管理员查看所有用户文档的调用需要重新设计专门授权接口。
2. **引用更严格。** 没有引用、空回答或非法编号会转为拒答，不再把未引用的所有片段附到答案后假装有依据。这可能增加真实模型的拒答率，必须用实际模型和数据评测。
3. **空文档列表有明确含义。** `doc_ids=[]` 表示没有可检索文档；省略或 null 才表示本人全部文档。
4. **会话只记录完整回合。** 失败、断流不保存一半对话；成功回合按完成顺序保存。跨客户端并发的同一会话暂未串行化。
5. **索引签名引入迁移门槛。** 旧向量缺签名或签名不同，启动时拒绝静默使用。换新数据库、从原始文件重导；或临时以 none 模式使用旧全文索引。
6. **哈希维度不再暗中截到 256。** 实际维度遵循配置。代码默认 1024，`.env.example` 选择 256；切换前已有数据库时应使用新库。
7. **文档复用不是错误。** 返回独立 `reused` 字段，`error` 只记录失败。并发重复上传可能返回 `indexing` 状态，调用方应检查状态。
8. **API 错误不暴露上游正文。** HTTP 返回通用错误，流内错误也不包含密钥/上游响应。日志仍应按内部数据管理。

## 5. 检索性能实验

命令：

```powershell
.\.venv\Scripts\python.exe scripts/benchmark_retrieval.py --chunks 10000 --dim 256 --repeat 3
```

实验设置：随机种子 42、10000 个归一化合成向量、每向量 256 维、Top-20、热缓存、每种方法重复 3 次。参考实现按原始策略加载正文和全量矩阵并完整排序；新实现使用分批精确检索。

| 方法 | 中位耗时 | tracemalloc 跟踪峰值 | Top-20 |
| --- | ---: | ---: | --- |
| 全矩阵参考实现 | 150.30 ms | 30.96 MB | 基准 |
| 分批精确实现 | 114.78 ms | 1.63 MB | 与基准一致 |

本次跟踪内存峰值减少约 **94.7%**，中位耗时减少约 **23.6%**。原始 JSON 已保存为 [benchmark-2026-10-22.json](benchmark-2026-10-22.json)。

限制：这是单机合成数据、单请求、特定维度的比较；tracemalloc 不是完整进程 RSS；没有测真实模型调用、冷缓存、并发吞吐、多用户负载或大文件解析。新实现仍然是 O(ND) 精确扫描，不应据此承诺“10 万片段几十毫秒”或生产吞吐量。

## 6. 教学评测结果及其解释

数据：3 份演示文档、9 个片段、12 个问题（8 个可回答、4 个不可回答）。模型：fake-extractive；向量：hashing-1024；Top-K=5。

| 指标 | 本次结果 |
| --- | ---: |
| Recall@5 | 1.0 |
| MRR | 1.0 |
| 引用文档命中率 | 1.0 |
| 关键词命中率 | 1.0 |
| 无答案拒答准确率 | 1.0 |

这些问题专为教学语料编写，数量很小，表达直接。满分只说明样例闭环跑通，不能证明泛化能力，也不能证明真实生成模型的事实正确性。新增业务文档后，需要独立标注的开发集和留出集。

指标口径：当前每个可回答问题只有一个 gold_doc，所谓 Recall@K 是目标文件在 Top-K 片段中是否出现的平均值；MRR 也是按首次目标片段排名计算。引用命中只检查文档名，不检查逐句支持性；同名文件会影响评测识别，真实数据应使用稳定文档 ID 和版本。

阈值扫描只按已有 confidence 模拟检索门槛，不会重新执行生成与引用校验，不能当作不同阈值的最终回答准确率。

## 7. 未完成能力与下一阶段优先级

| 阶段 | 触发条件 | 下一项改进 | 明确验收 |
| --- | --- | --- | --- |
| 近期：质量 | 准备接真实业务问题 | 独立标注 30~100 个问题、真实向量与重排器消融 | 留出集提升且错误案例可解释，记录成本/P95 |
| 近期：恢复 | 上传耗时长或必须抗重启 | 持久索引任务、租约、重试与取消 | 索引中杀进程，重启后恢复；重复任务不重复入库 |
| 近期：会话 | 多终端同时操作 | 会话请求顺序或版本控制 | 两客户端并发不混乱；失败可重试且不重复保存 |
| 中期：数据 | 多版本制度和复杂资料 | 原文存储、版本有效期、OCR/表格结构 | 能追溯版本；撤回立即停止召回；扫描件有明确处理状态 |
| 中期：容量 | 真实压测显示向量扫描瓶颈 | ANN / 独立检索后端 | 同数据同问题比较召回、P95、删除/权限一致性 |
| 中期：协作 | 组织共享与授权需求 | 项目/组织权限、审计日志和共享撤回 | 每个入口验证最小权限，撤回在检索与会话中生效 |
| 部署前 | 需要对外服务 | HTTPS、网关大小限制、共享限流、备份恢复、指标告警 | 形成恢复演练、负载测试和故障操作手册 |

其他明确边界：

- 没有调用真实付费模型，没有验证供应商兼容性和模型成本。
- 提示词约束不等于完整的提示注入防护；引用检查也不等于语义事实验证。
- 原始文件未保留，模型或分块升级需要原始文件重导。
- IDF 缓存有界，但每次语料版本改变仍会扫描该用户片段；大规模频繁更新可考虑增量统计。
- BM25 的语料统计来自共享 FTS 表；如果需要统计层面完全隔离，应采用独立租户索引。
- 上传在请求线程池执行，尚不是后台队列；业务层文件大小检查不能替代网关对整个请求体的限制。
- 健康检查只反映本服务与数据库基本状态，不证明上游模型可用。
- 单进程内存限流不适用于多实例统一配额；JWT 没有完整撤销列表与改密流程。
- 历史中保存的是当时的答案和片段引用；删除文档后旧会话记录不会自动抹去。需要保密撤回能力时，必须设计历史保留/删除政策与清理逻辑。

## 8. 建议使用方式

先按 README 运行本地演示，再按 [项目导读](PROJECT_GUIDE.md) 从入口追到数据库与检索，最后按 [12 周路线](LEARNING_ROADMAP.md) 逐项实验。每次继续升级时保留本轮测试和评测作为基线；不要只比较最终界面或一两个成功答案。
